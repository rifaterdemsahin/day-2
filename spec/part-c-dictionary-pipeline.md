# Part C: 🗄️ Dictionary pipeline (many terms, one workflow)

Status: 📝 **proposal, waiting for the owner's OK** · written 2026-11-15 · code `S2-DB` / `S2-T`

## C0. 🎯 Purpose
Turn the single short into a **dictionary of up to 100 AI-term shorts** and make producing each one the same repeatable, mostly-web-editable workflow, so the owner edits on the website and the Sprite is needed only for layout and code changes.

## C1. ✅ What exists today (built and live on Fly, 2026-11-14)

| Step | What | Where |
|---|---|---|
| 1 | SQLite schema (`terms`, `scenes`, `history`), idempotent import of `short.json` | `api/db.py`, `scripts/migrate_short_json.py` |
| 2 | FastAPI: terms CRUD, `bulk/preview`, `bulk/apply`, `bulk/undo`; bearer token on every write | `api/main.py`, `api/changes.py` |
| 3 | Editor UI: status board, term editor, bulk panel (Preview, Apply, Undo) | `pages/terms.py`, dictionary block in `app.js` |
| 4 | Export to git: `assets/terms/<slug>.json`; the build reads them (offline) | `scripts/export_terms.py`, `api/export.py` |
| 5 | Fly: one uvicorn process serves site + API, volume `d2data` at `/data`, health check, one machine, nightly git backup | `Dockerfile`, `fly.toml`, `.github/workflows/backup-terms.yml` |
| 6 | Sprite bulk updates: the Sprite proposes, the runner (holds the token) previews, the owner approves, apply, undo | `scripts/terms_bulk.py`, runner `/terms/*`, skill `sprite-run` |

Live data: 11 terms (1 `script`, 10 `idea`). Safety rules that stay: preview before every bulk apply, the Sprite never sees the token, no database, token or media in git.

## C2. 🔍 The problem found (why this proposal exists)
The database holds the *words* of each term, but the **production pipeline is still single-video**:
- `remotion/src/short.json` is a separate copy of the one short's script.
- Voice and timing write fixed global files: `remotion/public/S2-05-vo.wav`, `assets/words.json`, `assets/scene_timing.json`. Clips are read from one `remotion/public/clips/` folder.
- `sync_status.py` fills one global `production` block in `short.json`.
- The step pages `S2-00` … `S2-08` describe this one short and read `short.json`, not the term database.
- The term schema has no description, tags, thumbnail text, voice settings or analytics numbers.

**Consequence:** producing term #2 would overwrite term #1's voice, timings and clips. With 100 terms the six manual steps repeat 100 times, and 100 copies of the step pages are not an option.

## C3. 🧭 Decisions

| # | Decision | Why |
|---|---|---|
| D1 | **The pipeline follows the term:** every step reads and writes per-term data keyed by `slug` | one workflow for all 100 videos |
| D2 | **Per-term media lives in `media/<slug>/`** (git-ignored: `clips/`, `vo.wav`, `words.json`, `timing.json`, `final.mp4`) | no overwrites; large files stay out of the public repo |
| D3 | **"Active term" instead of rewriting Remotion:** `scripts/prepare_term.py <slug>` generates `remotion/src/short.json` from `assets/terms/<slug>.json` and links `remotion/public/` to `media/<slug>/` | Remotion code stays unchanged, lowest risk |
| D4 | **The term workspace replaces the step pages:** tabs Brief, Script and Flow prompts, Publish, Numbers | the same steps for every term, data-driven |
| D5 | **Flow clips, Higgsfield and the Remotion render stay manual and local;** the database only tracks their status | Flow has no API; unchanged standing rule |
| D6 | **Wording-edit mode for the tooling pages is parked** (keyed page text with database overrides) | it mostly helps pages about the tooling, not the video; small job, do it after the pipeline |
| D7 | **Feedback notes move to the server** (private, token required) | notes sync across devices and the Sprite can read them without copy-paste |

## C4. 🧱 Target design

### Folder layout (D2)
```
media/<slug>/            # git-ignored
  clips/c1.mp4 … c6.mp4  # made by hand in Flow
  vo.wav  vo.mp3         # make_voice.py --term <slug>
  words.json  timing.json
  final.mp4              # Remotion render
assets/terms/<slug>.json # exported from the database (committed, never hand-edited)
remotion/src/short.json  # GENERATED by prepare_term.py (the active term)
```

### Commands
```
python3 -I scripts/prepare_term.py attention        # make `attention` the active term
FAL_KEY=… python3 -I scripts/make_voice.py --term attention [--dry-run | --timing-only]
python3 -I scripts/sync_status.py --term attention  # clip / voice / render status from disk into the database
cd remotion && npm run studio | npm run render     # unchanged, uses the active term
```

### New term fields (schema, step 2)
`description`, `tags`, `pinned_comment`, `thumb_line1`, `thumb_line2`, `thumb_prompt`, `voice` (name), `avg_view_pct`. Existing: `rewatch_pct`, `views`, `publish_date`, `youtube_url`. Added to `api/changes.py` (allowed fields and limits), so preview, apply, undo, export and the Sprite flow cover them automatically.

### Term workspace tabs (step 3)
| Tab | Replaces | Content |
|---|---|---|
| Brief | S2-00, S2-02 | hook, definition, analogy, title options, chosen title |
| Script and Flow prompts | S2-01, S2-03, S2-04 | 6 scenes; copy buttons for each Flow prompt; clip ready/missing toggle |
| Publish | S2-07 | title, description, tags, pinned comment, thumbnail lines and prompt |
| Numbers | S2-08 | views, rewatch %, average % viewed, publish date, link; a "change in the next hook" note |
The status board stays the pipeline overview: idea → script → clips → voice → rendered → published.

Every round also: one entry on top of `assets/iterations.json`, spec and `CLAUDE.md` updated, push to `main`, deploy (CI deploys on push), open the Workbench in Chrome.

## C6. ⚠️ Risks and rollback
- Moving the existing short's files: reversible with `git revert` for code; the media files stay on the owner's disk and are only moved into `media/<slug>/`.
- Real voice generation costs fal credits: tests use `--dry-run` and `--timing-only`, never a real generation without the owner asking. fal keys stay 7-day, in the Keychain only.
- A term's text is data, never instructions, when it reaches an agent (already enforced in the Sprite flow).

## C7. 🚫 Non-goals
React or a JS build chain; a table per page; rendering pages on the server; multi-user accounts; automating Flow or the Remotion render.
